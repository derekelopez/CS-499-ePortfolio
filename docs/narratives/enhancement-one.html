Module 3 Milestone Two: Enhancement One: Software Design and Engineering

Artifact: Smart Thermostat

For my software design and engineering enhancement, I chose the smart thermostat application that I worked on in CS350 class. The project is a Python application designed to run on a Raspberry Pi and interact with several physical components, including an AHT20 temperature and humidity sensor, red and blue LEDs, three push buttons, a 16x2 LCD display, and serial communication. The original thermostat uses three operating states, which are Off, Heat, and Cool. These states allow the user to cycle between states and adjust the temperature setpoint. The LEDs provide visual feedback based on the current mode and temperature, while the LCD displays the current temperature, date and time, operating state, and setpoint.

I selected this artifact because it is a great example of the interaction between software and physical hardware while also providing a great opportunity for software engineering improvement. The original design works as intended, but the hardware initialization, thermostat logic, display management, serial communication, and timing are contained in a single program. This makes the code more tightly coupled to Raspberry Pi and makes it more difficult to test the thermostats decision logic without having the physical hardware connected.

I included the smart thermostat in my ePortfolio because it demonstrates several skills that are important in software development, including Python programming, object-oriented design, embedded system development, state-based application logic, hardware integration, testing, debugging, and configuration management. I think this is a valuable artifact enhancement because the enhanced version will show that I can create functioning applications, as well as evaluate an existing design, identify weaknesses, and refactor the software into a more maintainable structure.

The most significant improvement I have achieved is separating the thermostat’s decision-making logic from the Raspberry Pi hardware. I created a hardware independent thermostat_core.py module that has the thermostat states, setpoint logic, temperature validation, and LED decisions. The enhanced controller continues to use the original Off, Heat, and Cool behavior, but it no longer directly depends on GPIO, the AHT20 sensor, the LCD, or serial communication. This allows the core behavior to be executed and tested on a standard computer without requiring the actual Raspberry Pi.

I also improve the handling of the thermostat setpoint. The original application allowed the setpoint to be increased or decreased without limits. The enhanced version defines a minimum setpoint of 50 degrees Fahrenheit and a maximum of 90 degrees Fahrenheit and prevents the value from moving outside that range. Temperature inputs are also validated and unreasonable values are rejected.

Another improvement was removing the use of floor() from the control decision. In the original application, the measured temperature was converted to a whole number before the thermostat determined if heating or cooling was required. The enhanced controller retains the complete floating-point value for control decisions and only requires rounding when data is displayed or reported.

I created a separate config.py module to centralize settings that were previously hard coded throughout the application. This includes the default, minimum, and maximum setpoints; LED and button GPIO pins; LCD dimensions and pin assignments; serial settings; timing intervals; and sensor validation limits. Centralizing these values reduces the number of places that must be modified if the hardware configuration changes and makes the software easier to maintain.

Automated testing is another major improvement. I created unit test for the hardware-independent thermostat controller and used pytest to test the default state, state transitions, setpoint changes and limits, heating behavior, cooling behavior, Off behavior, and invalid temperature handling. All 13 automated tests are currently passing. This is an example of how the new architecture is more testable than the original.

The outcomes I identified for this enhancement in Module One were course outcomes 2, 3, 4, and 5. I think that the enhancement has already made great progress toward each of these outcomes, although I am continuing to work to complete the final integration.

Course outcome 2 focuses on professional communication. I am addressing this outcome through the organization of the enhanced source code, descriptive module and method documentation, the code review, and the planned ePortfolio documentation.

Course outcome 3 involves designing and evaluating computing solutions while also considering design tradeoffs. This enhancement supports that outcome because I can compare the original tightly coupled structure with a modular architecture. The new design requires additional modules and introduces more structure, but the additional complexity provides great benefits, including lower coupling, improved testability, easier maintenance, and clearly defined responsibilities.

Course outcome 4 involves using appropriate computing techniques and tools to implement solutions that provide value. The enhanced thermostat demonstrates this through modular Python design, automated testing, validation, configuration management, and hardware abstraction. These techniques improve the reliability and maintainability of the thermostat without changing its purpose.

Course outcome 5 focuses on developing a security mindset. I have begun addressing this outcome through defensive validation of temperature and setpoint values and separating configuration from application logic. I will also add safer exception handling, controlled logging, dependency review, resource cleanup, and careful handling of future communication settings.

One important thing I learned from this enhancement is that working software in not necessarily well-designed software. The original thermostat performed its required tasks, but reviewing it from a software engineering perspective showed me that functionality was only one part of the application. Because the thermostat logic directly referenced hardware objects, even a simple test of the state and temperature logic depended on Raspberry Pi libraries and physical equipment. Refactoring the application forced me to think more about separation of these parts of the program.

Automated testing also changed the way I approached the artifact. Instead of verifying every behavior manually through LEDs and buttons, I can now test the controller on my computer and confirm that state transitions, setpoint boundaries, and heating and cooling decisions behave correctly. Having 13 repeatable tests provides stronger evidence than manually observing the device once. I learned that designing for testability can influence the architecture of a program from the beginning instead of being added after development is complete.

The primary challenge has been improving the architecture without changing the behavior that already works. The thermostat still needs to preserve the original Off-to-Heat-to-Cool state sequence, existing GPIO wiring, LED behavior, buttons, sensor, and LCD functionality. For this reason, I made the enhancement incrementally instead of rewriting the entire project at once. I first isolated and tested the controller, then centralized configuration, and then began creating the Raspberry Pi hardware layer. This approach makes problems easier to isolate and reduces the risk of introducing errors.
