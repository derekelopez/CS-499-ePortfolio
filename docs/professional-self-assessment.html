Professional Introduction

I am completing my Bachelor of Science in Computer Science with a concentration in Software Engineering at Southern New Hampshire University. My academic work, together with my professional experience in ergonomics and process improvement, has helped me approach software development as a disciplined process of identifying needs, evaluating alternatives, testing results, and communicating decisions. I am especially interested in software architecture, embedded systems, algorithms, backend development, databases, and secure programming.

My CS-499 capstone portfolio demonstrates that progression through three enhancements of two earlier course artifacts. I refactored a Raspberry Pi Smart Thermostat for improved software design and engineering; improved a Pirate Intelligent Agent and compared A* pathfinding with a deep Q-network (DQN); and extended the thermostat with a Flask API and MongoDB-based telemetry storage. Together, these artifacts show my ability to move beyond initial functionality toward maintainability, measurable performance, system integration, and responsible assessment of limitations.

Outcome One — Collaboration and Organizational Decision-Making

Effective collaboration in computer science depends on making code and design choices understandable to people who may have different technical responsibilities. During the Module Two code review, I evaluated my original Smart Thermostat and Pirate Intelligent Agent implementations, identified areas for improvement, and communicated an enhancement plan through a recorded technical presentation. The review gave me practice explaining what existing code does, why a change is warranted, and how the change can be evaluated.

In the thermostat enhancement, I separated configuration, core thermostat behavior, physical hardware operations, and application orchestration into distinct modules. This organization allows another developer or reviewer to focus on one responsibility without first understanding an entire monolithic script. For the intelligent agent, I documented corrected movement and reward handling and compared algorithm outcomes using the same maze and starting positions. Those results provide evidence to support a design decision instead of relying on preference alone.

These were individual capstone projects, not a claim that I worked on a formal development team. Nevertheless, I applied collaborative practices that would support a team: meaningful file organization, contextual documentation, reproducible comparisons, Git version control, and explicit acknowledgment of design trade-offs. I learned that a productive code review should be specific, respectful, actionable, and based on shared goals.

Outcome Two — Professional Oral, Written, and Visual Communication

I communicated the capstone work through a code review video, three written enhancement narratives, source-code documentation, testing summaries, and a public GitHub Pages portfolio. These formats serve different audiences. Source files and algorithm details support technical reviewers; project overviews and architecture explanations help stakeholders understand why the work matters; and the public portfolio provides employers with direct access to the evidence behind my stated skills.

For example, the intelligent-agent narrative explains A* in terms of its priority queue, path-cost tracking, Manhattan-distance heuristic, and computational trade-offs. It also presents results clearly: A* solved 50 of 50 evaluated starting positions, whereas the DQN solved 1 of 50 in the recorded training and evaluation configuration. I explicitly avoid generalizing those findings to every reinforcement-learning problem. Similarly, the thermostat telemetry documentation traces the flow of readings from the Raspberry Pi through the Flask API into MongoDB.

The process reinforced the importance of consistent naming, precise technical language, accessible navigation, and matching claims to evidence. An effective technical portfolio should allow a reader to locate original and enhanced artifacts, understand the changes, and inspect supporting results without unnecessary obstacles.

Outcome Three — Algorithmic Design, Evaluation, and Trade-Offs

The Pirate Intelligent Agent provides my strongest evidence of algorithmic evaluation. The original project used deep Q-learning to navigate a treasure maze. I improved maze constructor validation, handling of invalid actions, and reward-ordering behavior, then implemented A* search as an alternative with an explicit heuristic. The A* implementation uses a priority queue, cost tracking, parent relationships, and Manhattan distance to guide search and reconstruct a path.

In a recorded evaluation using an 8-by-8 maze and 50 valid starting positions, A* found paths from all 50 starts, with a mean successful path length of 15.64 moves. The DQN succeeded from one start (2%) after the recorded training run of up to 1,000 epochs. Its single successful route required one move, so that average is not meaningful as a cross-algorithm efficiency comparison. The evidence supports choosing A* for this known, deterministic maze under the tested conditions, while recognizing that DQN has different strengths and that additional training or tuning could change its results.

This work emphasized that algorithm selection depends on assumptions and constraints. A* requires accessible state and movement information and uses memory for its frontier and path records, while DQN incurs training cost and has performance sensitive to reward design and learning configuration. I also considered complexity, including graph-search costs and the memory required to maintain candidate states. In the thermostat, I used a clear OFF/HEAT/COOL state model and bounded setpoint logic to solve a different type of deterministic control problem.

Outcome Four — Computing Techniques, Tools, and Practical Value

I used iterative development and testing across embedded software, algorithm research, and backend services. The thermostat runs on Raspberry Pi hardware with buttons, LEDs, an LCD, and temperature/humidity readings. I refactored the application into modules and then verified that the display, three operating states, setpoint controls, heating and cooling indicators, and clean shutdown continued to operate. Separating the core from hardware access also supports more focused unit testing.

For the database enhancement, I implemented a Python telemetry client, Flask REST endpoints, a validation layer, and MongoDB persistence on a Windows host. I verified that the Raspberry Pi could send readings, the API could process them, and records appeared in MongoDB. The system also supports querying stored telemetry for analysis. For the intelligent agent, I used Python, Jupyter, TensorFlow, and heap-based search to implement and measure competing approaches.

These enhancements reflect stages of the software development life cycle: assessing the original artifact, planning changes, implementing incrementally, testing behavior, interpreting results, and documenting what remains. They deliver practical value by improving maintainability, supporting evidence-based algorithm selection, and creating a record of embedded-device behavior. The projects remain educational prototypes; I would plan additional reliability, deployment, and operational testing before treating them as production systems.

Outcome Five — Security Mindset and Responsible Design

The capstone work strengthened my understanding that security begins with requirements and architectural decisions, not merely with a final scan. In the thermostat, setpoint constraints and separation of responsibilities reduce opportunities for invalid input or unintended changes to affect control logic. In the Pirate Intelligent Agent, validating maze dimensions and cell values and handling invalid states helps prevent malformed input from producing unpredictable behavior.

The telemetry enhancement introduces a network boundary and persistent data, which require additional care. I separated request validation from Flask routing and database operations, and I reviewed source files for obvious credential patterns before publishing the repository. However, input validation alone does not make an API production-secure. Authentication, authorization, encrypted transport, database access restrictions, stronger error handling, and deployment hardening require further verification or implementation before exposing the service outside a trusted development environment.

I also considered how future changes could affect assumptions: new thermostat fields would require corresponding validation and database handling; additional maze rules would affect pathfinding; and changes to API behavior would require new tests. The main lesson is to document trust boundaries, validate data explicitly, limit unintended access, and state which security measures have been implemented versus those that remain future work.

Professional Growth and Future Direction

These capstone enhancements changed how I judge software quality. A successful demonstration is only a starting point. I now place greater emphasis on whether code can be explained, maintained, tested, evaluated, and safely extended. My professional background has taught me to look for root causes and communicate improvements in a way that supports decisions; the capstone allowed me to apply that perspective to software design.

Going forward, I intend to deepen automated testing, strengthen API authentication and transport security, improve deployment documentation, and expand my work in software engineering and connected systems. This portfolio represents verified progress toward those goals: refactored embedded software, an evidence-based algorithm comparison, and an end-to-end telemetry application. It is also a record of how I approach new technical challenges—with analysis, iteration, measurement, and clear communication.
